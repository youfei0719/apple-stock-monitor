# 运维手册（StockMon）

## 服务一览

| 服务 | systemd | 端口/路径 |
|---|---|---|
| API | `stockmon-api` | 127.0.0.1:8101 |
| 监控引擎 | `stockmon-engine` | 独立进程 |
| 前台 | nginx static | `/opt/stockmon/frontend/dist` |
| 后台 | nginx static | `/opt/stockmon/admin/dist` → `/admin/` |
| 备份 | cron 每天 3:10 | `deploy/backup.sh` |

常用命令：`systemctl status|restart stockmon-api stockmon-engine`；日志 `journalctl -u stockmon-api -f` + `/opt/stockmon/logs/`。

### 日志文件（R7 日志方案 a：API 与 engine 各写各的）
- `stockmon-api.log` / `stockmon-engine.log`：structlog JSON 应用日志，**真实路径 `/opt/stockmon/backend/logs/`**（`logging.py` 默认 `log_dir="logs"`，相对 systemd `WorkingDirectory=/opt/stockmon/backend`；目录由 `os.makedirs` 自动创建，无需手动建）。两个进程各写各的（`TimedRotatingFileHandler` 非多进程安全，双进程共用一个文件午夜 rollover 会竞态）。unit 里 `STOCKMON_LOG_NAME` 决定文件名，本地直跑未设置时回退 `app.log`。轮转由 `TimedRotatingFileHandler` 自带（保留 30 天），**logrotate 不覆盖这里**（copytruncate 与 `TimedRotatingFileHandler` 混用有截断风险）。
- `api.out.log` / `api.err.log`、`engine.out.log` / `engine.err.log`：systemd `StandardOutput/StandardError` 捕获的 stdout/stderr，路径 `/opt/stockmon/logs/`。
- `backup.log`：backup.sh 的 cron 输出（`/opt/stockmon/logs/backup.log`）。
- 轮转：`logrotate-stockmon.conf` 覆盖 `/opt/stockmon/logs/*.log`（每日、保留 14 天、copytruncate；只覆盖 stdout/stderr 捕获与 backup 日志）——新文件名已在 `*.log` 通配内，无需改配置。

## 首次部署完整步骤（R5-D-5）

前提：服务器 Debian/Ubuntu（root），域名 `stock.glint.red` 已解析到本机公网 IP，80/443 端口对外开放。

### 1. 把仓库传上服务器（二选一）

- **方式 A（推荐）：git clone**——在服务器上直接拉仓库（deploy.sh 的 bootstrap 也是这条路，脚本会自动处理）：
  ```bash
  # 先手动克隆一次，把脚本拷到位；之后 deploy.sh 自己会 git pull
  mkdir -p /opt/stockmon && git clone https://github.com/youfei0719/apple-stock-monitor.git /opt/stockmon/repo
  ```
- **方式 B：scp 传脚本**——本机没 git 或想先审脚本：
  ```bash
  scp -r deploy/ root@<服务器IP>:/opt/stockmon/repo/deploy/
  # 注意：方式 B 下 deploy.sh 开头的 git clone/pull 仍会工作（会补全整个仓库）
  ```

### 2. 在服务器上手动建 .env（R5-D-5）

```bash
cp /opt/stockmon/repo/.env.example /opt/stockmon/.env
chmod 600 /opt/stockmon/.env
vim /opt/stockmon/.env   # 逐项填真实值
```

**必填项清单**（填完再跑脚本，否则 deploy.sh 会报错退出）：
- `APP_SECRET_KEY`：`openssl rand -hex 32` 生成，禁止留 `change-me-64hex`
- `APP_ENV=prod` 时的硬门槛：`AFDIAN_TOKEN`、`AFDIAN_PLAN_STANDARD`、`AFDIAN_PLAN_PRO`、`SMTP_HOST`、`SMTP_USER`、`SMTP_PASSWORD`（缺一不可，prod 启动会 RuntimeError）
- `SSL_EMAIL`：certbot 注册邮箱（如 `SSL_EMAIL=youfei8722@gmail.com`），首次申请证书用
- `TRUSTED_PROXIES=127.0.0.1`（nginx 反代场景，否则登录限流把所有用户算成同一个 IP）
- `ADMIN_EMAIL` / `ADMIN_PASSWORD`：首个管理员账号（首次启动自动创建，之后可清空密码字段）
- `BASE_URL=https://stock.glint.red`、`FRONTEND_URL=https://stock.glint.red`

⚠️ **安全警告（R5-D-N8）**：deploy.sh 用 `set -a; source .env` 加载配置，`source` 会执行命令替换和变量展开。**.env 里不要写 `$(...)`、反引号**——脚本以 root 执行，写进去的命令会被直接执行。

⚠️ **行尾注释禁令（R10-P0-1，R11-P1-7 已扩展到所有 key）**：`.env` 里**禁止行尾注释**。systemd `EnvironmentFile` 不剥行尾注释，`APP_ENV=prod  # 生产` 会被服务读成 `"prod  # 生产"`（`is_prod` 误判 → 生产跑 dev 语义：prod 硬门槛失效、HTTPS cookie 丢 Secure 标志），而 deploy.sh 校验阶段是剥掉注释看的——不拦截就是静默污染。注释一律写在独立行；deploy.sh 发现值含引号外的 `#` 会直接报错退出（引号感知：`PASSWORD='a#b'` 这类引号内的 # 合法，不误伤）。

⚠️ **CRLF（Windows 行尾）陷阱（R10-P2-3）**：bash `source` 不剥 `\r`，`APP_ENV=prod\r` 同样污染值。用 LF 行尾编辑 `.env`；deploy.sh 会在 `source` 前自动清洗 CRLF 并告警（原文件原地改写）。

### 3. 跑一键部署

```bash
/opt/stockmon/repo/deploy/deploy.sh
```
⚠️ 首次部署必须用仓库路径 `/opt/stockmon/repo/deploy/deploy.sh`。`/opt/stockmon/deploy` 软链接是脚本自己在 bootstrap 阶段建的（指向 `$REPO/deploy`），首次部署前它还不存在，别去找。
脚本会做：root 检查 → 前置软件检查（git/python3-venv/node/npm/nginx/curl/sqlite3/rsync/certbot/crontab，缺哪个报哪个）→ .env 校验（含行尾注释/CRLF/export 前缀拦截）→ 拉代码 → systemd units → **申请证书（certonly，不改写手写 nginx conf；certbot 失败也有 ERR trap 恢复 nginx）** → nginx 生效 → 后端 venv/依赖/ruff 门禁 → 前后端构建 → migrate（R10-P1-D1：构建成功后、重启前，避免构建失败留下"新库+旧代码"中间态） → 健康检查（等引擎心跳 60s）。

### 4. 首次部署人工盯一次 certbot 输出（待联调）

certbot 与自带 SSL stanza 的 nginx conf 在真机首次部署时可能交互异常（如 80 端口被占、域名未解析、standalone 拿证失败）。**首次部署时请人工盯一次 certbot 的完整输出**，确认出现 `Congratulations!` / 证书路径后，再看 `nginx -t` 和 `DEPLOY OK`。后续续期由 certbot timer 自动执行（renewal 配置已写入 `--pre-hook/--post-hook/--deploy-hook`），无需人工：续期时会自动先停 nginx 独占 80 端口拿证、再启动并 reload，**nginx 会有数秒短暂中断，属正常**。可用 `certbot renew --dry-run` 手动验证续期链路。

### 5. 验证

- `curl -sf https://stock.glint.red/healthz` → `{"status":"ok",...,"engine":"running"}`
- 浏览器打开 `https://stock.glint.red`（前台）与 `https://stock.glint.red/admin/`（后台）
- `systemctl status stockmon-api stockmon-engine` 均为 active

## 开关与调度

### ENGINE_ENABLED（引擎开关）
- `.env` 里 `ENGINE_ENABLED` 默认 `false`：API 进程（`stockmon-api.service`）不启动引擎。
- 独立引擎进程由 `deploy/stockmon-engine.service` 启动，unit 里显式 `Environment=ENGINE_ENABLED=true`，是**全站唯一**的引擎运行者。
- 严禁在 API 进程的环境里把开关打开（双引擎重复轮询/重复通知）；手动在 shell 跑 `python -m app.services.engine` 会走 fail-fast 检查，开关未开直接拒绝启动。
- 排查"引擎没在跑"：`curl /api/admin/system` 看 `engine.running`（读引擎写进 DB 的心跳，60s 内有心跳 = running），或 `journalctl -u stockmon-engine`。

### membership_sweep（会员生命周期调度）
- 不是 cron：跑在引擎进程内，每 60 tick（默认 tick=5s，约 5 分钟）执行一次 `run_lifecycle_sweep`（`backend/app/services/lifecycle.py`）。
- 做三件事：① standard/pro 到期自动降级（到期后切换 `pending_tier`，降级后超限任务自动暂停）；② 到期前 3 天 / 1 天续费提醒（邮件）；③ 僵尸任务 nudge（断裂链路，见代码注释）。
- 排查：日志搜 `lifecycle_sweep_failed`；单子 sweep 异常只记日志，不中断引擎主轮询。

### SQLite WAL（写并发）
- 应用内连接默认 `PRAGMA journal_mode=WAL` + `busy_timeout=5000`（`backend/app/core/db.py`），读/写可并发，写锁等待 5s 再报错。
- 备份脚本（`deploy/backup.sh`）用 `PRAGMA busy_timeout=15000`（15s），与引擎写锁撞车时多等一会儿；备份失败（产物为空/完整性校验不过/前置检查不过）走 `fail()`：**写日志 + SMTP 发失败告警 + 非零退出**，cron 会感知到。
  - 告警收件人优先级：`BACKUP_ALERT_TO`（.env 可选，模板里有注释行）> `SSL_EMAIL` > `SMTP_USER`；SMTP 配置缺失则跳过告警只记日志（prod 下 deploy.sh 已做 SMTP 硬门槛校验）。
  - Bark 不走：Bark key 是用户级通知渠道（存各用户任务配置里），没有运维全局 key。
- 注意：WAL 模式下库文件旁边有 `app.db-wal`/`app.db-shm`，恢复备份时三个文件视为一体；不要只拷 `app.db`。

## 订单处理（后台 /api/admin/payments）

订单状态：`paid`（已支付）· `amount_mismatch`（金额与档位不符，待人工）· `unknown_plan`（爱发电 plan_id 未知，待人工认领/定夺）· `refunded`（已标记退款）· `resolved`（人工关闭/处理完毕）· `cancelled`。

- **认领** `POST /api/admin/payments/{id}/claim {"user_id":N}`：未认领订单（用户赞助后没填邮箱/账号对不上）绑定用户 + 按订单档位开通 30 天（到期/配额锚点同步）+ 回填 `Payment.user_id`；若原状态为 `amount_mismatch`，成功后自动置 `resolved` 并待处理计数 -1。全程记审计。
- **关闭（不处理）** `POST /api/admin/payments/{id}/close`：人工定夺为"不予开通"时用。`status` 置 `resolved`（移出待处理队列），不绑定用户、不开通档位；`amount_mismatch` 时待处理计数 -1。记审计。
- **标记退款** `POST /api/admin/payments/{id}/refund`：`status` 置 `refunded`（收入统计只计 paid，自动排除）+ 该用户降回 `free` 并清空 `tier_expires_at`/`pending_tier`。**实际退款钱款在爱发电后台操作**，本接口只标记账务状态 + 联动降级。记审计。
- 待处理徽标（`pending_payments`）= `unclaimed` + `amount_mismatch`；上述三操作都会同步递减计数，徽标不会长期误报。

## 常见故障

### 1. Apple 接口被限流（541/403）
- 现象：任务状态大面积 `unknown`/`cooling`，日志 `apple_541_cooldown`。
- 处理：属预期行为，引擎会自动指数退避。检查：`curl /api/admin/system` 看限流状态；不要手动调高频率。
- 若持续 30 分钟以上：检查出口 IP 是否被 Apple 封禁，考虑启用 `PROXY_POOL` 轮换。

### 2. 邮件发不出
- 检查 `.env` 的 SMTP_HOST/USER/PASSWORD；用 `POST /api/notify/test` 自测。
- QQ/163 邮箱易进垃圾箱：优先用阿里云 DirectMail / SendCloud。

### 3. 爱发电支付回调失败
- 爱发电后台确认 webhook URL 为 `https://stock.glint.red/api/pay/afdian-webhook`。
- 检查 `AFDIAN_TOKEN` 是否正确；日志搜 `afdian_webhook`；失败订单在 `/api/admin/payments` 人工补单（改级）。

### 4. 后台无法登录
- 确认 `ADMIN_EMAIL/ADMIN_PASSWORD` 在 `.env`；首次启动自动建号，之后清空密码字段。
- bootstrap 建号时邮箱自动置为已验证（`R20-P3-4`，可信的部署者地址，无需再验）；若 403 `email_unverified`，检查该账号 `email_verified` 是否为 1。
- TOTP 丢了：进库 `UPDATE users SET totp_secret=NULL WHERE email='x'` 后重新绑定。

### 5. 磁盘/备份
- 备份在 `/opt/stockmon/backups`，保留 14 天。
- **备份失败告警**：`backup.sh` 任何一步失败都会经 SMTP 发告警邮件（收件人见"开关与调度/SQLite WAL"）。如果 SMTP 没配（dev 环境可能），告警会被跳过——这时**无自动告警，需人工定期检查**：
  ```bash
  tail -n 50 /opt/stockmon/logs/backup.log        # 看最近一次备份是 ok 还是 FAIL
  ls -lt /opt/stockmon/backups | head              # 确认每天有新产物
  ```
- **⚠️ 恢复警告（WAL 模式必读）：WAL 模式下库由 `app.db` + `app.db-wal` + `app.db-shm` 三个文件组成，视为一体。恢复前必须先 `systemctl stop stockmon-api stockmon-engine`（两个服务都停），再 restore，否则正在运行的进程可能持有旧 WAL 句柄、把恢复写丢或损坏库。**
- 恢复步骤（服务已停的前提下）：
  ```bash
  DB=/opt/stockmon/backend/data/app.db   # 默认路径；改过 DATABASE_URL 时，
                                         # 以 deploy/backup.sh 的 P0-26 解析结果为准
                                         # （相对路径以 /opt/stockmon/backend 为基准）
  systemctl stop stockmon-api stockmon-engine
  # R10-P1-D2：WAL 残留先收拢——服务崩溃后残留的 -wal 与 restore 进去的新主库帧
  # 不匹配，下次打开有损坏风险。wal_checkpoint(TRUNCATE) 把帧并入主库，
  # 确认 -wal/-shm 无残留后再 restore。
  sqlite3 "$DB" "PRAGMA wal_checkpoint(TRUNCATE);"
  rm -f "$DB-wal" "$DB-shm"
  [ -e "$DB-wal" ] || [ -e "$DB-shm" ] && { echo "ERROR: -wal/-shm 仍存在，请排查后再 restore"; exit 1; }
  sqlite3 "$DB" ".restore '/opt/stockmon/backups/app-YYYY-MM-DD.db'"
  cp /opt/stockmon/backups/env-YYYY-MM-DD /opt/stockmon/.env && chmod 600 /opt/stockmon/.env
  systemctl start stockmon-api stockmon-engine
  ```

## 发布流程
`/opt/stockmon/deploy/deploy.sh` 一键重部署（含 migrate + 前后端构建 + 健康检查）。首次部署先看本手册"首次部署完整步骤"（传脚本→手建 .env→跑脚本→人工盯 certbot）。

## 本地开发前置（R6-P2-17，R7 修正说法）
- **`data/` 下的 sqlite 文件不会随仓库来**：`backend/data/` 和 `*.db` 被 gitignore，克隆后 `data/` 是空的。**migration 脚本是随仓库来的**（`backend/alembic/versions/` 在 git 里），本地首次跑必须先建库/migrate，否则 API 会因表缺失报错。
- 本地首次建库（pydantic 的 `env_file=".env"` 按**当前目录**解析，所以先把 `.env` 放到 `backend/` 下）：
  ```bash
  cd backend
  cp ../.env.example .env   # 填好 DATABASE_URL（默认 sqlite:///./data/app.db 即 backend/data/app.db）
  python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
  .venv/bin/alembic upgrade head   # 在 backend/data/app.db 建库到最新 revision
  ```
- 之后校验：`.venv/bin/alembic check` 应无漂移报错；再 `uvicorn app.main:app` 即可启动。
