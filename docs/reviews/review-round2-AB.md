# 第二轮产品逻辑审查 · A/B 维度（会员与配额体系 / 监控任务生命周期）

## 一、断裂

### 断裂-1：会员到期永不降级——一次付费，终身会员
- 依据：`models.py:32`（`tier_expires_at` 字段）；`pay.py:124-126`（仅写入）；`quota.py:31`、`admin.py:110`（仅展示）。全库 grep：没有任何代码读取 `tier_expires_at < now` 做降级，`deps.py:get_current_user` 不检查过期，engine 取档位直接用 `t.user.tier`（`engine.py:162,171`）。
- 场景复现：用户付 ¥19 开标准会员，30 天后依然是标准版——100 次/月推送、30 秒刷新、历史权限永久保留。收入闭环彻底漏水。
- 成熟做法：每日低频 job 扫描过期 → 降级 free + 发"已到期"通知 + 3~7 天宽限期；超限任务（>3 个）自动暂停多出的。
- 修复建议：独立低频 job：`tier_expires_at < now 且 tier != free` → `tier='free'` + 通知；宽限期 7 天后再暂停超出 free 上限的任务。到期前 3 天/1 天各发一次续费提醒。

### 断裂-2：持续提醒可一夜烧完月度配额，无任何护栏
- 依据：`schemas.py:60,81`（`repeat_interval_sec` 无 `ge` 下限）；前端 `AddMonitor.tsx:134-136`（`ri > 0` 就接受，1 秒都行）；`engine.py:239-249`（到期即 `notify=True`）；`engine.py:251-256`（每次 `_fire` 扣 1 次配额）。
- 场景复现：标准会员（100 次/月）监控持续有货 SKU，`repeat_interval_sec=60` → 每 60 秒扣 1 次 → 100 分钟烧完月度配额，之后整月所有任务静默（只写 skipped）。3 个门店按 (store,part) 独立计数，烧得更快。DING果卖次数包、用户对次数有强感知；我们是包月固定次数 + 用户可自配间隔无限加速消耗，无换算公式/预计烧完提示/间隔下限/80% 预警。
- 成熟做法：重复间隔下限（如 ≥1 小时）；设置时显示"预计月消耗 ≈ X 次"；80% 推送预警（不扣配额）；耗尽自动暂停任务并明确提示。
- 修复建议：后端 `repeat_interval_sec` 加 `ge=3600`；前端显示预估消耗；配额 80%/100% 发预警；耗尽时自动 `paused=True` 并任务卡标红。

### 断裂-3：体验版 1 次推送用完后，任务"假活"
- 依据：`engine.py:285-300`（`_check_trial_quota` 超限返回 False）→ `engine.py:257-259`（`_record_skipped`，`channel="quota"`，`user_id=None`）。`_due_tasks`（`engine.py:153-173`）只看 `paused/expires_at`，配额耗尽的任务照样每 5 分钟轮询 Apple API、持续写 skipped。
- 场景复现：匿名用户体验，1 次推送用完 → 任务不暂停不降级，继续烧 Apple API；用户完全感知不到：① `/quota` 要求登录（`quota.py:19`）；② skipped 记录 `user_id=None`，`/notifications` 按 user_id 过滤，匿名用户无从查看；③ 前端任务列表仍显示"正常"。
- 修复建议：trial 配额耗尽 → 自动 `paused=True`，前端任务卡显示"体验推送已用完，去注册/升级"；或给匿名任务可见的配额状态接口。

### 断裂-4：任务过期后"无声死亡"，且显示过期旧状态误导用户
- 依据：`engine.py:157`（过期任务排除出轮询，此后无归档/通知/清理）；`tasks.py:43-51`（`_display_state` 六态里没有 expired）；`tasks.py:112-121`（`list_tasks` 无过期分区）；前端 Home.tsx 无续期按钮，TaskDetail.tsx 无操作按钮（续期只能调 PATCH，前端无入口）。
- 场景复现：任务 `expires_at` 一到 → 停止轮询，但躺在列表里显示最后一次轮询的旧状态（如 `available`）——用户误以为"还在监控/有货"。匿名 trial 任务强制 24h 过期（`tasks.py:26-40`），过期后永久堆积在 DB，无清理 job。
- 成熟做法：过期前 3 天/1 天提醒；过期任务进"已过期"分组、状态置灰标注；一键续期；过期 30 天归档删除（通知记录保留）。
- 修复建议：加 `expired` 展示态；列表分"监控中/已过期"；过期前提醒；trial 过期任务 7 天后物理删除。

### 断裂-5：重复任务 → 重复通知 + 重复扣配额
- 依据：`tasks.py` 的 `create_task`/`batch_create` 均无 `(user, part, stores)` 查重。引擎 `_group_tasks`（`engine.py:176-186`）按 (city, part) 合并 Apple 请求（不重复打 Apple API ✓），但 `_process_task` 按 task 独立维护 `StockState`、独立 `_fire`、独立扣配额（`engine.py:210-260`）。
- 场景复现：用户批量生成不小心提交两次（batch 接口无幂等）→ 同一次到货发 2 条通知、扣 2 次配额。标准会员 100 次/月直接腰斩。
- 修复建议：创建时对 `(user_id, part_number, store_numbers集合)` 做冲突检测，409 提示"已存在相同任务"；或提供"合并重复任务"一键清理。

### 断裂-6：登录后体验任务"消失"，后台继续跑、关不掉
- 依据：匿名任务 `user_id=None` + `device_id` 绑定（`tasks.py:148-149`）。`list_tasks`（`tasks.py:112-121`）：`if user: 按 user_id 查 elif x_device_id`——登录后永远走 user 分支，体验任务不可见；`_get_owned`（`tasks.py:216-225`）登录态下操作 device 任务直接 403。
- 场景复现：用户体验后注册登录 → 旧任务在后台继续每 5 分钟轮询（烧 Apple API），每月还能再触发 1 次 trial 推送（device 配额独立），用户看不见、暂停不了、删除不了。
- 修复建议：注册/登录时把同 device 的匿名任务迁移绑定到 `user_id`（一次性认领），或登录后提示"发现 1 个体验任务，是否接管"。

### 断裂-7：长期无货的僵尸任务永无出路
- 依据：无。没有任何"连续 N 轮无货 → 提示/自动结束"机制；`expires_at=None` 的任务可永久轮询。DING果"100次发不出任务自动结束"的对等机制不存在。
- 场景复现：用户建任务监控冷门 SKU，长期无货 → 任务永久占用任务名额（`quota.py:28-30` 全量计数）、永久消耗 Apple API；前端不展示"已连续无货 X 天"。
- 修复建议：连续无货 30/60/90 天各发一条提醒（不扣配额）；加"自动结束"开关（默认开：连续 90 天无货自动暂停并通知）。

## 二、不自洽

### 不自洽-1：降级立即生效，用户当场丢失已付费权益
- 依据：`pay.py:120-127`：`base = tier_expires_at if 未来 else now; user.tier = tier_to; tier_expires_at = base + 30天`。无论升降级都是当场改写 tier。
- 场景复现：pro 用户还有 20 天到期，付 ¥19 降到标准 → 当场失去 pro 权益，剩余 20 天 pro 价值不折算、不退款。升级倒是慷慨（剩余 standard 天数免费变 pro），但降级逻辑与"到期生效"常规做法矛盾。
- 成熟做法：升级立即生效，降级到期生效。
- 修复建议：webhook 判断方向：`tier_to` 低于当前档 → tier 保持到 `tier_expires_at`，记 `pending_tier`，到期 job 再切换。

### 不自洽-2：会员周期（购买日+30天）vs 配额周期（自然月 UTC）错位
- 依据：会员 `pay.py:126` `timedelta(days=30)`；配额 `engine.py:271` `period = utcnow().strftime("%Y-%m")`（自然月 1 号 0 点 UTC = 北京时间 8 点清零）。trial 配额同样按月（`engine.py:291-292`）。
- 场景复现：10 月 25 日付费 → 会员到 11 月 24 日，但配额 11 月 1 日重置（多拿约 1/4 个月配额）；10 月 31 日付费 → 10 月配额只有 1 天可用。DING果是 7 天/30 天周期制，会员与次数周期语义统一。
- 修复建议（二选一）：① 配额周期改为购买日对齐的 30 天滚动；② 保持自然月，但在 `/plans` 和前端明确标注"每月 1 号（北京时间 8 点）重置"。

### 不自洽-3：配额口径——"推送次数"到底是事件数还是通知条数
- 依据：一次 `_fire` 只扣 1 次配额（`engine.py:251-256`），但 `Notifier.dispatch`（`notifier.py:114-165`）会向 bark + 多个 webhook + email + sms 每个渠道各发一条。前端 `Me.tsx:27` 写"月推送 X 次"。
- 场景复现：配了 bark+邮箱+企微的用户，1 次配额换 3 条实际通知。用户理解的"推送次数"与计费口径不一致，成本模型被低估。
- 修复建议：明确口径——文档/前端写"按触发事件计次，多渠道同一次事件只计 1 次"；或改为按渠道条数计次。

### 不自洽-4：删除任务后，通知历史的 part_number 变空
- 依据：删除 `db.delete(task)`（`tasks.py:248-252`），`StockState` 级联删除（`models.py:121`），`Notification.task_id` 外键 `ondelete="SET NULL"`（`models.py:147-149`）→ `history.py:76` 对已删任务显示 `part_number=""`。
- 场景复现：用户删任务后去"有货历史"看，看到一条无 part_number、无门店名的"幽灵"通知。
- 修复建议：`Notification` 加 `part_number` 冗余字段，删除任务时快照保留。

### 不自洽-5：暂停的任务占不占配额——代码自洽但未向用户说明
- 依据：暂停任务不轮询/不触发/不扣配额（`engine.py:156` 过滤 paused ✓），但任务名额照占（`quota.py:28-30` 全量计数）。逻辑本身合理，但前端和 /plans 说明里 nowhere 提到"暂停仍占名额"。
- 修复建议：前端任务卡暂停态下加 hint"暂停中（仍占 1 个任务名额）"。

## 三、对标差距
1. 配额预警 + 耗尽自动暂停：DING果通知按次消耗、剩余次数强感知、100 次发不出自动结束；我们剩余次数只在"我"页小字展示（`Me.tsx:107`），无预警、无自动结束 → **必须补**
2. 到期降级/续费提醒/宽限期：DING果有完整到期语义；我们会员永不过期 → **必须补**
3. 重复任务去重：DING果按门店维度监控；我们批量生成易产生重复任务导致重复扣配额 → **必须补**
4. 微信通知：DING果核心特权；我们只有 bark/企微/钉钉/飞书/邮件（sms 占位未实现，`notifier.py:88-90` raise NotImplementedError，tiers.py 已主动不开放 ✓）→ 可以晚点
5. 全国城市榜单数据口径：我们 `/ranking` 只是该用户自己的有货事件聚合，DING果是全平台真实放货榜单 → 可以晚点
6. 刷新间隔：DING果会员 3 秒刷新；我们 pro=10s、standard=30s（`config.py:86-89`）→ 可以晚点
7. 新品期免费用户禁手动查询：DING果防薅；我们无手动查询入口，免费档靠 5 次/月 + 300s 间隔限流 → 不用做
8. 购买指南：我们有 `guide.py` + 通知直达 SKU 页/购物袋兜底（`notifier.py:24-31`）→ 基本持平 ✓
9. 通知直达到货 SKU 页：已实现 ✓

## 修复优先级
**P0（上线前必须修）**：断裂-1（会员永不过期）→ 断裂-2（持续提醒烧配额）→ 断裂-4（过期任务误导性展示）→ 断裂-5（重复扣配额）→ 断裂-3（体验任务假活）→ 断裂-6（登录后任务消失）→ 断裂-7（僵尸任务）
**P1（首版体验完整性）**：不自洽-1 → 不自洽-2 → 不自洽-3 → 不自洽-4 → 不自洽-5
**P2（对标补齐）**：微信通知 → 全平台城市榜单 → 3 秒刷新档

一句话总结：配额与会员两套体系各自都"能跑"，但会员没有到期、配额没有护栏、任务没有终点——三个"没有"都是闭环上的洞。
